## 判断

1. **优势仍成立，但适用范围更窄。** 全根准确计数/限量输出仍明显占优，完整输出在本轮
   连续布局后也领先 STR；全根仍是特殊场景，没有赋予默认业务权重。
   高命中重叠视口的 count/cap64/all 优势仍有支持，但含大量空查询的小视口/小选框不普遍领先。
   均匀非全根查询，候选即使改善后仍落后 STR；不能推广旧固定位置负载的优势。
2. **保留连续布局。** 它同时降低候选处理和输出读取成本，完整输出收益尤其明显。
   10 万均匀非全根 count 两轮降低约 16–24%，all 降低约 10–28%；
   均匀全根 all 降低约 54–58%，聚簇全根约 37–38%。构建没有重复退化，
   线性容量没有增加，并删除了长期保存的 order。改动小且不改变查询工作量，因此值得保留。
   这不是所有负载的性能保证：旧顺序下聚簇射线 all 两轮观测退化 18.4% 和 8.8%，平衡顺序复测未重复。
3. **足够支持下一轮独立静态 BVH/STR 原型实验，但不足以直接替换生产。**
   均匀小选框平均每批仅命中 47 个对象，却测试 19,677.875 个；均匀小视口对应
   290.375 / 21,530。候选数量与直接读取成本是不同问题，本轮没有减少候选数。
   新原型应继续同语义、同传输对照，覆盖构建频率、预算、退化与真实业务轨迹；
   本次没有创建第二套生产索引，也没有恢复内容边界。

## 实现、公开语义与成本

构建仍先校验输入并生成原有节点和 DFS order；随后按 order 一次性生成最终 Entry 数组，
最终仅保存新条目数组、节点和统计。查询与 node_object_id 改为 entries[i]。
数组中是按 DFS 顺序排列的 Entry 值/引用，没有逐坐标重建 AABB，
不意味着 Entry 内的几何对象在堆中连续，也不是 SoA。

外部 UInt32 ID、NodeInfo 的编号/单元边界/深度/直属对象数/孩子掩码、node_object_id
的直属对象顺序保持不变。重复 ID 和根外错误仍使用重排前的输入位置。
查询集合、准确总数、恰好填满 Complete、容量不足 Truncated、实际访问/测试口径均不变；
公开生成接口无差异。order_capacity 字段保留，按最终存储的实际容量返回 0。

构建新增 O(N) 索引读取和 N 个 Entry 数组槽复制；重排期间新旧两个条目数组与 order
同时存在。最终不再长期持有 N 个 Int32 的 order（逻辑载荷 4N 字节，另有数组表示）。
旧条目槽和 order 在构建结束后可释放，AABB 没有做第二套坐标深复制。
这些是源码可核实的逻辑复制量，不是实测活跃堆峰值，也不能简单推算为整个索引节省 4N 字节。
下面构建比较包含重排及释放，不是单独计时重排循环；不将较低中位数宣称为重排本身零成本。

## 退化和限制

- 10 万聚簇射线 all：第一轮 1.520 → 1.800 ms，第二轮 1.595 → 1.735 ms，
  约退化 18.4% / 8.8%。该射线轨迹在聚簇数据全部无命中，仍复制全容量输出；
  工作统计一致，原因可能涉及代码生成、分配/GC 与传输相位，本轮没有隔离因果。
- 10 万聚簇小视口 all 第二轮 1.485 → 1.500 ms，小选框 all 1.430 → 1.455 ms；
  第一轮相应改善，不能宣称所有完整输出都加速。
- 1 万聚簇射线 cap64 两轮 0.020 → 0.025 ms、0.015 → 0.020 ms；
  第一轮聚簇中视口 all 0.175 → 0.190 ms（+8.6%）。小规模没有排除这些退化。
- 1 千聚簇小视口 count 第二轮约 0.005 → 0.010 ms；相对倍数很大而绝对差极小。
  本次样本常见间隔约 0.005 ms，极短查询的比例不应当作稳定效果。
- 重叠小视口/小选框中，候选虽然优于基线，仍慢于 STR；高命中重叠场景才更有优势。
  均匀非全根仍整体落后，聚簇不同位置差异大。所有数据保留，不作业务加权平均或“胜率”宣传。
