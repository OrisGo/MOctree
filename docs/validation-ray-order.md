# 射线调用顺序修正与两轮复测

2026-10-25。从干净的 70a2de9 创建 codex/fix-benchmark-order。
本次只改基准和文档，连续布局生产源码及 before/after/STR 模块哈希与此前完全一致。

## 问题与修复

旧调度以 step%8 选批次、step%2 选射线首后端，每个批次总是同一版本先运行，
第二轮也重复绑定。旧 9–18% 退化是真实观测，但不能排除调用顺序影响。

当前 batch=i%8，cycle=floor(i/8)，first=(batch+cycle+phase)%后端数。
射线每八批翻转顺序；三后端也逐周期移动首位置。调度在计时外生成，
schedules.ray 保存每个样本批次和后端顺序。专项每轮 128 样本、32 预热，
每批在每个调用位置恰好出现 8 次；第二轮 phase=1，反转对应样本的起始顺序。
这是顺序控制，不是显著性检验；仍不能排除 GC、缓存和热状态影响。

## 复测与结论

同机 Chrome 156.0.8078.47 / V8 15.6.75.19，Ryzen 7 8845HS，
moon 0.1.20261020 / moonc 0.10.16+b1a0e846e，Node 22.23.1。
每轮隔离 Chrome，顺序运行，计时期间没有编译、测试或 profiler。
覆盖三规模、三分布、count/cap64/all 和 before/after，每轮 54 行；
每批 8 条、八批一个周期，沿用原射线坐标。全部组合预先对照独立扫描，
总命中、写入、ID 和工作统计一致。STR 只参与构建、资源及共同域检查，不参与射线排名。

10 万聚簇 all：第一轮 1.670 → 1.535 ms（-8.1%），第二轮 1.630 → 1.625 ms（-0.3%）。
**新复测没有重复旧退化，旧结果不足以建立稳定退化判断。**
预热由 20 增至 32、样本由 100 增至 128，运行时间和热状态也不同，
不能把新旧差异全部归因于顺序，更不能保证所有射线负载没有回退。
原 AABB 收益证据和保留连续布局的决定不变；本次未重跑完整 AABB/STR 延迟矩阵。
旧数据不删除、不改写；两轮范围不是置信区间。
