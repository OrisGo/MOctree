## 热点证据与解释

下表百分比为同名函数在所有调用上下文的 **self 样本**之和，再除以该份 profile 总样本数。
两轮分别计算；不是精确 CPU 耗时，也不是整体加速潜力。父子 inclusive 不相加。

| 场景 | 两轮证据 | 判断及限制 |
| --- | --- | --- |
| 均匀小选框 count，MOctree | `run_query` 两轮均约 96.9%；每批命中 47、测试 19,677.875、访问 573 节点 | 查询核心主导，输出不是主要因素；大量不命中对象测试值得优先减少，仍需诊断其深度与归属 |
| 聚簇中选框 count，MOctree | `run_query` 99.2% / 99.0%；每批命中 33,237.875、测试 41,765.25 | 与小选框不同，很多判断确有命中；不能把所有扫描视为无效工作，需分批观察空帧与高命中帧 |
| 均匀小选框 all | MOctree `output_u32` 72.1% / 67.6%；STR 92.1% / 83.6% | 即使少命中，当前 ABI 复制预留的 8N 个 UInt32 槽；应单独验证传输成本，不能归因于树遍历 |

## 下一步最小验证实验

1. **候选扫描归属诊断。** 独立诊断模式按深度、直属对象数量、跨分割面归属统计测试/命中。
   先回答小选框的 19,678 次测试集中在哪里，再评估剪枝或构建选择；探针不混入正式计时，
   不改变单归属、内部节点检查和准确总数契约。暂不恢复已否决的内容边界优化。
2. **输出传输拆分实验。** 保留现有 ABI 作为基线，量化预留槽复制与有效结果复制的差距。
   任何改变输出布局、未写区或生命周期的方案先明确契约影响，不直接改生产；全部输出、限量、
   零命中和恰好填满都需要扫描对照。仅有火焰图还不能宣称可获得相同比例加速。
3. **构建成本拆分。** 分开首次构建、重复重建及释放，记录临时容量和分桶分配。
   `moonbit.gc.free` 是运行时释放路径，不能直接解释为 JS 垃圾回收停顿。

本阶段已完成第一批可追溯诊断，尚未实施上述生产优化。当前没有逐节点热力图、真实业务轨迹、
硬件缓存计数或精确分配峰值；这些未知项不能由函数名或数组布局推断。
