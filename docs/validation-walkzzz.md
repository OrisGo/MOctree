# walkzzz Octree 与 MOctree：点数据浏览器对照

2026-10-25。从干净的 `36f569f` 创建 `codex/bench-walkzzz-points`。生产核心和已有适配接口未修改。
固定 `walkzzz/moon-geometry@0.251.0`（MIT），比较普通 Octree、Loose Octree 与 MOctree 的零尺寸 AABB 适配。
本实验不是有体积 AABB 对比，也不表示 MOctree 已新增生产点云功能。
与 MoonSTRtree 的分域结论、动态更新边界及后续热力图/火焰图任务见 [对比总结](comparison-summary.md)。

## 结论

- **基础点插入和构建：walkzzz 更快。** 10 万点三种分布，两轮普通 Octree 构建比本次 MOctree 适配快约 2.3–3.2 倍。
  MOctree 还承担 AABB/ID 校验、批量构建、DFS 重排及坐标映射存储，不能将差值全部归因于树构建算法。
- **局部查询：没有全面领先者。** 均匀小视口 count/cap64，普通 Octree 两轮均较快；Loose Octree 两轮均慢于 MOctree。
  中选框、完整坐标输出、聚簇空帧混合负载存在小差距和轮间变化，不能宣称 MOctree 普遍快于另一种 Octree。
- **整体包含：MOctree 明显占优。** 全根 count/cap64 免逐点判断，walkzzz 的现有 API 必须先生成完整命中数组。
  全根 all 三种分布两轮均由 MOctree 领先；此结论是本次坐标输出适配后的端到端结果。
- **重复坐标/分割面：仍有弱项。** 全部原点的内部子区查询触及八个闭合盒，不能按集合去重。
  MOctree 的 count/cap64 两轮都慢于普通 Octree，退化幅度不稳定；all 第 1 轮较慢、第 2 轮较快。
- **资源：不能宣称 MOctree 更轻。** 本基准的 MOctree 点适配模块更大，10 万点构建后线性容量更高。
  这包含为输出坐标保留的额外点表，不能当作核心索引纯内存比较。

## 环境与方法

Ryzen 7 8845HS（16 逻辑 CPU）、24,429,539,328 字节内存；Linux 7.2.11-200.fc44.x86_64；
Chrome 156.0.8078.47、V8 15.6.75.19；Node 22.23.1；moon 0.1.20261020、moonc 0.10.16+b1a0e846e。
全部为 release stripped wasm。两轮各一个隔离 Chrome，会话内三后端交替测量，第二轮 phase=1。
每轮 324 行：三规模 × 三分布 × 四查询 × 三输出 × 三后端；每行 96 批次样本、24 次预热。
每批 8 条查询，每序列 8 批，每个批次在各后端位置恰好 4 次。构建每组 5 个独立实例。
正确性验证、数据准备、checksum、页面更新和资源探针均在计时外。没有并行编译或 profiler。

三方输入均为 3N Double，输出统一为三坐标；MOctree 以序号为 ID 并映射回坐标，walkzzz 返回 Point3D。
因此没有把返回 ID 的 4 字节和返回坐标的 24 字节直接混为同样输出成本。
MOctree 并非专用点索引，两方内部存储、校验和 API 不同；本实验不隔离纯算法性能。
普通 Octree 阈值 16，Loose Octree 阈值由源码固定为 8、松散因子 2；三者深度 16，MOctree 节点预算 2N+1。
未做参数搜索；walkzzz 没有查询原生 count/限量接口，桥先取全部结果再计数/截取。

## 根外点与父节点行为复现

固定版本、根中心 (0,0,0)、边长 200；插入 (500,0,0)，查询 [499,-1,-1]–[501,1,1]：

- 普通及松散 Octree 插入返回正常，整树 count/size 为 1，但范围查询为 0。
- MOctree 零尺寸 AABB 构建明确拒绝该根外对象，未参与性能排名。
- 普通 Octree 在 capacity=2、连续插入五点后，已有孩子的根节点再次持有两个点；整树与全根查询均为五点。
  这是已复现的组织行为，不据此声称错误或性能劣势。

最小复现位于 [独立测试](../benchmarks/walkzzz/tests/behavior_test.mbt)。根外查询缺失适合向作者确认
是输入前置条件、需要补文档还是应拒绝/扩根；当前公开函数本身没有报告该错误。
本次没有向上游提交 Issue。没有把源文件注释中的复杂度承诺当作实测证明。
