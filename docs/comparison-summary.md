# MOctree、MoonSTRtree 与 walkzzz：对比结论与下一阶段定位

2026-10-25。本报告汇总已归档实验，没有新增性能测量。生产实现采用 DFS 连续条目布局；
点共同域实验来自 `dde7e25`。各次测量的源码及模块哈希以对应原始记录为准，不能用当前 HEAD 替代。

## 结论与适用场景

MOctree 当前定位是浏览器 WASM 中批量构建、只读查询的 Double AABB 对象索引。
它在整体包含、准确计数及限量输出上有明确优势，但没有全面领先其他索引。
“适合读多写少”描述的是当前使用方式，不代表所有读取都更快，也不代表已经支持少量增量写入。

| 对比域 | 已有证据 | 仍然薄弱或未验证 |
| --- | --- | --- |
| MOctree 与 MoonSTRtree 0.2.2：有体积 AABB | 全根 count/cap64、全根完整输出，以及部分高命中重叠负载支持 MOctree 的优势 | 均匀局部查询仍落后；聚簇必须区分空帧、高命中帧，不能给统一排名 |
| MOctree 点适配与 walkzzz/moon-geometry 0.251.0：零尺寸 AABB/点 | 全根 count/cap64 明显领先；全根 all 三分布两轮均领先；聚簇内部子区有优势 | 普通 Octree 构建更快；均匀小范围 count/cap64 略快；重复点分割面查询仍有弱项 |
| 资源与动态场景 | 已记录模块大小和线性内存容量；MOctree 提供预算与明确结果状态 | 不等于低内存冠军；尚无三方动态更新吞吐、活跃堆峰值或真实业务帧率对照 |

AABB 和点实验是两个共同域，不能合成三方总榜。点实验额外包含 MOctree 的 ID→坐标映射，
不能把点适配的构建、容量或延迟直接作为生产 AABB 索引的结果。
walkzzz 的本次桥先获得完整命中结果，再实现 count/cap64；STR 的 count 使用专用
`query_count`，不生成命中数组，只有 cap64 先取完整结果再截取。
因此优势包含公开 API 与适配方式的贡献，不是纯树算法倍率，也不是最近邻 top-K 比较。

## 代表性证据

同机 Ryzen 7 8845HS、Linux、Chrome 156.0.8078.47 / V8 15.6.75.19、
MoonBit 0.10.16+b1a0e846e、release wasm。以下均为 10 万条目、每批八条查询，
数值是两轮各自 p50 的范围，不是置信区间；不能除以八冒充单条查询分位数。

| 实验 / 场景 | MOctree（ms/批） | 对照（ms/批） | 解读 |
| --- | ---: | ---: | --- |
| AABB 均匀小视口 count | 0.315–0.325 | STR 0.055–0.060 | 局部查询仍有明显差距 |
| AABB 均匀小选框 count | 0.300–0.435 | STR 0.045–0.060 | 平均命中 47 个，却测试约 19,678 个对象 |
| 点均匀小视口 count | 0.070–0.080 | 普通 Octree 0.060–0.070 | 差值较小，不宣称稳定大幅领先 |
| 点均匀全根 all | 36.655–40.335 | 普通 Octree 46.760–50.070 | 本次统一坐标输出下 MOctree 更快 |
| 重复原点内部子区 count | 4.210–12.610 | 普通 Octree 3.685–3.745 | 两轮都落后，退化幅度不稳定 |

点实验中，普通 Octree 构建比 MOctree 点适配快约 2.3–3.2 倍。
均匀/聚簇 10 万点构建后线性容量为 MOctree 40 MiB、普通/Loose Octree 20 MiB；
完整输出后均为 40 MiB。容量包含临时分配及分配器保留，不是活跃堆，也不能据此算精确内存节省。
MOctree 点适配模块为 21,051 字节，walkzzz 两种树共用模块为 14,327 字节，不能推广为各生产库最小体积。

局部 AABB 的大量对象测试是已观察事实；“STR 更快是因为候选更少”仍是待验证解释，
因为现有 STR 桥没有公开 visited/tested 统计，记录为 null，不能推导双方候选数量比。
连续布局降低处理成本，但没有减少候选数。内容边界实验因构建、容量和部分查询代价未保留。
旧聚簇射线 all 的退化在平衡顺序复测中未重复，不能继续作为已确认稳定回退。

## 动态变化边界

| 操作 | MOctree 当前生产类型 | 本次对照的 MoonSTRtree 0.2.2 |
| --- | --- | --- |
| 相机、选框或查询区域移动，索引对象不变 | 可重复查询 | 可重复查询 |
| 对象移动、旋转或缩放后，索引坐标系中的 AABB 改变 | 需重新构建 | 需重新构建 |
| 对象增删 | 需重新构建 | 需重新构建 |

MoonSTRtree 0.2.2 的依赖 README 明确构建后不可变、数据变化需要重建；公开核心接口已核对。
其围栏监测更新接口不等于底层三维树的增量更新。walkzzz 的本轮构建使用逐点插入，
但没有测对象移动、删除或更新维护成本，不能据此认定它适合每帧动态场景。
MOctree 动态类型仍是规划，见 [架构边界](architecture.md)和[契约](contracts.md)。

- 先从现有原始记录生成两套独立矩阵：AABB 对 STR，点对普通/Loose Octree。
  行为分布与查询场景，列为规模与 count/cap64/all；两轮分别展示，不只选较好一轮。
- 延迟比统一为 `MOctree / 对照`，大于 1 表示 MOctree 更慢；采用以 1 为中心的对数色标，
  同时展示双方绝对延迟、单位、样本数和 p50/p95/p99。零值或缺失值标为不可比较，避免无穷倍率。
- 增加 visited_nodes、tested_objects、total_hits、written 和实际输出字节的视图。
  对方未提供的统计显示“未提供”，不能填零；零命中不计算 tested/hits 比率。
- 聚簇按八个批次的命中情况展开空帧与高命中帧，避免总体 p50 隐藏代价。
  另列构建、模块体积和内存容量，不混入查询延迟分数，也不建立无业务权重的综合榜。

- 每个后端和场景单独采样；固定输入、容量、批次及迭代次数，预热后采集 Chrome CDP
  `.cpuprofile`，用既有 MoonFlame 0.2.0 渲染。MoonFlame 负责展示，CPU 数据由 Chrome 采样。
- 使用保留名称的分析模块，记录其源码及模块哈希；正式排名仍使用未开 profiler 的 release 模块。
