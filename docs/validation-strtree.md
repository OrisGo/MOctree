# MoonSTRtree 三维对照实测

> 本报告是子树整体命中和连续条目布局优化之前的历史对照。当前适用范围请结合[对比总结](comparison-summary.md)，不要直接使用下表评价当前实现。

2026-10-25 北京时间 19:40–19:42，完成 162 组浏览器对照。
MOctree、MoonSTRtree 和独立 JS 扫描各通过 30 项共同域校验，全部计时组合通过扫描对照。
本轮没有修改 MOctree 算法或公开契约，也没有实施 PCL/OrthoTree 对照。

**结论：MOctree 构建更快，在全重叠数据上查询有优势；均匀和双簇数据的多数查询明显落后于
MoonSTRtree。没有测到整体查询领先、更小模块或更低线性容量。** 这是本次固定参数和数据下的结论。

## 测量口径

- MOctree 核心基线 `edc6a3a`，未修改；MoonSTRtree 固定为发布包 `LING71671/moon_strtree@0.2.2`。
- AMD Ryzen 7 8845HS，16 逻辑 CPU；Linux 7.2.11-200.fc44.x86_64；Chrome 156.0.8078.47 headless，V8 15.6.75.19。
- MoonBit moon 0.1.20261020 / moonc v0.10.16+b1a0e846e；Node 22.23.1；两套模块均 release stripped wasm。
- 固定种子 20261025，1 千/1 万/10 万对象，均匀/双簇/全重叠；局部与全根 AABB；计数/限量/全部输出。
- 每批 8 条查询，20 次预热、100 次采样；独立实例构建 5 次。构建和查询均轮换后端顺序。
- 同一 JS 块传输包装器；包含输入/输出复制、各自公开 API 的分配和校验成本。
- 计时期间没有 profiler、资源探针或并行编译；分位数为 nearest rank。

[原始记录](../benchmarks/results/2026-10-25T11-40-12-794Z-strtree-chrome.json)保存原始样本、模块和源码哈希、
依赖源码清单、环境及校验结果；[运行方法与完整限制](../benchmarks/strtree/README.md)提供复现步骤。

## 10 万对象的查询

单位为 **毫秒/批次的 p50**，不能当作单条查询延迟。下表所有输出模式都要求准确总命中数。

| 分布 / 查询 | 输出模式 | MOctree | MoonSTRtree | JS 扫描 |
| --- | --- | ---: | ---: | ---: |
| 均匀 / 局部 | 只计数 | 0.295 | 0.030 | 5.910 |
| 均匀 / 局部 | 最多 64 ID/条 | 0.310 | 0.035 | 6.175 |
| 均匀 / 局部 | 全部 ID | 1.945 | 1.495 | 6.215 |
| 均匀 / 全根 | 只计数 | 64.585 | 12.155 | 6.185 |
| 均匀 / 全根 | 最多 64 ID/条 | 58.395 | 11.955 | 7.895 |
| 均匀 / 全根 | 全部 ID | 72.860 | 16.000 | 9.315 |
| 双簇 / 局部 | 最多 64 ID/条 | 22.515 | 6.520 | 4.825 |
| 双簇 / 全根 | 最多 64 ID/条 | 42.895 | 13.280 | 6.170 |
| 全重叠 / 局部 | 最多 64 ID/条 | 5.290 | 8.175 | 6.230 |
| 全重叠 / 全根 | 只计数 | 5.435 | 7.145 | 6.270 |
| 全重叠 / 全根 | 最多 64 ID/条 | 5.295 | 8.205 | 6.240 |
| 全重叠 / 全根 | 全部 ID | 10.860 | 11.655 | 9.575 |

均匀局部限量查询中，MOctree p50 约为 STR 的 8.9 倍；均匀全根限量约为 4.9 倍。
全重叠全根限量查询，MOctree 耗时减少约 35.5%。这表明“只需修复全根查询”不足以解释全部差距，
低命中局部查询的剪枝和每个候选的处理成本也应分析。

54 个匹配负载组合中，MOctree p50 更低 24 个、更高 29 个、相等 1 个。
这是固定矩阵的观测计数，不是胜率、显著性检验或实际业务权重；小规模样本可能接近计时分辨率。
原始记录保留 p95/p99 及所有样本，不能从单个 p50 推导稳定尾延迟优势。

限量模式中，STR 的三维公开 API 先生成所有命中，再由桥截取；计数模式使用专用 `query_count`。
完整输出模式统一为每条预留 N 个槽，即使实际只命中少数对象也会复制整块缓冲；
因此均匀局部的完整输出耗时明显增加，不能把增加全部归因于树遍历。
STR 外部 UInt32 ID 映射也计入成本。双方未改成具有相同内部存储/分配方式的人工实现。

## 构建与资源

10 万对象，构建 p50（毫秒）：

| 分布 | MOctree | MoonSTRtree | MOctree 耗时减少 |
| --- | ---: | ---: | ---: |
| 均匀 | 51.075 | 198.825 | 74.3% |
| 双簇 | 41.765 | 190.990 | 78.1% |
| 全重叠 | 29.255 | 38.200 | 23.4% |

只采样 5 个独立实例，不能视为构建尾延迟承诺；此处包括输入传输、数据转换、校验与构建，
实例化不计入。均匀分布下构建节省约 147.75 ms，但每批局部限量查询多花约 0.275 ms。
若仅将这两项 p50 作粗略估算，约 537 批（4,296 条查询）后构建优势可能被查询差距抵消。
这只是固定负载的算术取舍，不是混合工作负载实测或选择阈值保证。

| 模块 | 原始字节 | gzip level 9 字节 |
| --- | ---: | ---: |
| MOctree 块传输 | 29,056 | 13,915 |
| STR 基准桥及所需代码 | 28,529 | 12,053 |

STR 模块只实现受控 AABB 基准桥，不含 MOctree 的完整错误/预算协议；体积不能当作功能等价产品排名。
也不能因为 MoonSTRtree 整库功能多，就假定裁剪后的 WASM 模块会很大。

新建 10 万均匀对象实例后，两者线性容量均从 64 KiB 增至 **43 MiB**；依次执行全根计数、限量、
完整输出各 20 批后，容量均未继续增长。此数值受分配器保留空间和增长粒度影响，
**相同容量不等于相同活跃堆、分配量或真实峰值**。目前无法主张 MOctree 更省内存。

## 实际验收与后续优先级

- Node debug/release：三个后端各 30 项共同域校验通过。
- Chrome：90 项共同域校验、162 个计时组合扫描对照及页面筛选检查通过。
- 独立模块 wasm check/build/info、格式检查及根仓库 prek 检查通过。
- 修复共享 Chrome 驱动的新页面执行上下文启动竞态后，原浏览器快速验收（36 组、70 项断言、
  三份 CPU profile 及 SVG 缩放/搜索/复位）再次通过；该快速运行不替代此前完整历史记录。

后续首先测清低命中局部查询中的节点访问与对象测试成本，再评估完整包含子树时的计数/输出优化。
原始基线应保留，优化后使用相同矩阵重新比较；不能只保留改进场景。
OrthoTree、PCL、其他浏览器、受限设备和真实峰值内存仍未验收。
