# 新版 MOctree 与 MoonSTRtree 浏览器复测

2026-10-25，基于优化提交 `74cfa25`，在独立分支 `codex/bench-subtree-strtree` 完成两轮完整对照。
结论：新版在全根计数、全根限量输出和全重叠查询上占优；均匀及双簇局部查询仍落后。
均匀全根完整输出仍慢于 MoonSTRtree，双簇全根完整输出接近但略慢。不能将整体包含计数的收益推广到所有查询。

## 环境和验收

- Ryzen 7 8845HS、16 逻辑 CPU、24,429,539,328 字节内存，Linux 7.2.11-200.fc44.x86_64。
- Chrome 156.0.8078.47 headless、V8 15.6.75.19；Node 22.23.1；moon 0.1.20261020、moonc 0.10.16+b1a0e846e。
- MOctree 与 MoonSTRtree 0.2.2 均为 release stripped wasm；同一浏览器会话内轮换后端采样。
- 每轮 162 行：1 千/1 万/10 万对象，三种分布，两种查询，三种输出，三个后端（包含 JS 扫描）。
- 每批 8 条查询，20 次预热、100 个样本；构建 5 个独立实例。第二轮使用新的隔离 Chrome 会话。
- 两轮各 90 项共同域校验通过，所有计时组合均与独立 JS 暴力扫描核对，页面筛选通过。
- 本次还运行 release Node 集成，三个后端各 30 项通过。两轮原始样本的分位数和测量源码哈希已核对。
- 与旧浏览器记录相比，Chrome/V8、基准脚本、STR 模块及依赖源码哈希一致。旧轮次仅用于趋势参考，不将跨轮次差值解释为纯算法收益。

全根 count/cap64 只访问每条查询的根节点、对象相交测试为零；准确命中每批 800,000 个对象。
这种负载下 MOctree 明显领先（两轮各组合约 269–458 倍），小于 0.1 ms 的绝对耗时接近浏览器计时粒度，倍数不应被视为稳定承诺。
完整输出仍需读取 ID、间接寻址和复制，均匀全根输出 MOctree 约慢 1.36–1.40 倍；双簇约慢 1.01–1.03 倍。
全重叠局部查询三个输出模式两轮均领先，但完整输出优势仅约 8%，仍需业务数据验证。

MOctree 三类构建均更快；每轮仅 5 个样本，不提供尾延迟保证。
模块为 MOctree 29,454 字节（gzip 14,121）/ STR 28,529 字节（gzip 12,053）。

## 仍需优化的场景及优先级

1. **均匀局部查询**：count 仍慢约 9.8–10 倍，cap64 慢约 7.6–8.4 倍。
   每批只命中 124 个对象，却测试 19,376 个对象、访问 740 个节点。
   相比优化前 19,388 次对象测试几乎不变。优先分析父节点跨分割面对象的候选过滤及扫描布局；
   可先测量紧凑条目存储、减少 order 间接读取的收益，再评估更复杂索引方案，不能承诺仅凭布局消除候选数差距。
2. **聚簇局部查询**：每批命中 400,000 个对象，但仍测试 313,032 个对象、访问 2,620 个节点。
   两轮不同输出模式仍慢约 2.48–2.95 倍。值得试验子树实际内容边界，使完全命中的判定更贴近数据，
   同时量化新增边界的构建、内存和稀疏查询成本；公开节点单元边界语义应保持不变。
3. **完整输出**：即使消除对象测试，均匀全根输出仍落后。优先分析输出 ID 读取及存储局部性。
   当前双方 all 模式均预留并复制 8N 个槽位；局部少命中时也有大块传输成本，不能将全部耗时归因于遍历。

这些属于下一轮建议，本次没有新增结构或修改核心算法。
STR cap64 由公开三维 query 生成全部命中再截取，count 则使用 query_count；本对照衡量现有 API 加适配的端到端成本，不能据此宣称纯算法全面领先。
两轮均仅有局部/全根查询，没有加入内部八分区负载、射线或跨设备矩阵；完整原始样本含 p95/p99，但未进行统计显著性分析。
